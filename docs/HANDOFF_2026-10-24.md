## Changes since the 23 October handoff

### Map packages, header, and setup

The map package inventory now covers the observed package files and a recommended decode order ([MAP_PACKAGE_FILES.md](MAP_PACKAGE_FILES.md), “Reading order for parity”). Static writer/loader work established the fixed `header.bin` prefix and a bounded reader for supported versions 121–124. Its leading version and text, selected camera/date fields, extended-block flag, and record-list counts have evidence-backed names. A separate setup trace verifies the start-year option mapping and terrain-dependent start days; several header slots are used as 0–2 option levels, but their UI names and meanings remain UNKNOWN. The header tail and the map’s water level, climate, and world-size meanings remain unresolved ([GAME_SETUP.md](GAME_SETUP.md), “Start date,” “Option slots behave as 0 to 2 levels,” and “Option-source xref follow-up”; [MAP_PACKAGE_FILES.md](MAP_PACKAGE_FILES.md), header inventory).

### Network format, kinds, and graphics overlay

The shared network record structure has been extended to eleven package files, including secondary roads/rails, pedestrian ways, heating, water pipes, power lines, conveyors, pipes, and rails; per-file support remains at the maturity shown in the package inventory. Trailing groups are structurally decoded as a u32 value, count, and segment indices. Their values and the purpose of secondary networks are not established ([MAP_PACKAGE_FILES.md](MAP_PACKAGE_FILES.md), “One generic network format, eleven files” and “What `road_secondary` is”).

The package-file-to-network-kind mapping and compiled per-kind constants are VERIFIED by static loader/setup traces. The meanings and units of network-object members are still UNKNOWN; proposed width and speed interpretations are INFERRED only. A 12 m nearest-neighbor spacing peak for disconnected road segments is OBSERVED and does not prove road width ([NETWORK_KINDS.md](NETWORK_KINDS.md), “File to network kind mapping,” “Interpretation status,” and “Data cross-check: 12 m spacing”). Segment kind/subkind distributions and some road-header fields are structurally understood, but road width, lanes, speed, surface, and construction cost remain UNKNOWN ([REVERSE_ENGINEERING_LEDGER.md](REVERSE_ENGINEERING_LEDGER.md), “Road segment header” and network-kind entries).

`OR_SHOW_NETWORKS=1` enables a presentation overlay for the decoded heating, water, pedestrian, and conveyor network files. A top-down N22 view showed spatially coherent pedestrian paths and heating/water mains (OBSERVED); colors and widths are OpenRepublic presentation choices. The sampled region showed no conveyor mesh (PROGRESS_LOG.md, actual Git time 23 October 12:32 EDT). On one RTX 5070 Ti view, the frame-limited update measurement was about 4.11–4.17 ms across new roads, `OR_OLD_ROADS=1`, and overlay variants. Because the app was capped at 240 Hz, this did not resolve small cost differences and is not a general performance result (PROGRESS_LOG.md, actual Git time 24 October 14:20 EDT).

`OR_WATER_ORIGINAL=1` selects the observed water-script color as a showcase comparison aid. A framed lake/river capture appeared greyer and lighter than the default water (OBSERVED); script-to-shader color space, channel interpretation, and blending remain unknown, so this is not a parity claim (PROGRESS_LOG.md, true Git interval 11:21–11:23 EDT).

### Building and worker record layouts

The `buildings_game.bin` placement writer was separated from `buildings.bin` runtime state. The per-building writer structure and its fixed blocks, vector counts, and copied fields have been mapped structurally, but none of the slots has an established gameplay meaning. A corpus scan covered 23,769 records in 44 of 65 packages; the other 21 lacked supported adjacent header versions and were not shown malformed. Earlier one-package slot patterns conflicted with the broader scan. The candidate +0x4a0 employed-worker interpretation is INFERRED and not supported by the later worker-reference comparison; do not name it as an accessor ([REVERSE_ENGINEERING_LEDGER.md](REVERSE_ENGINEERING_LEDGER.md), “Building save-state serializer trace,” “Per-building record, writer mapping,” “Per-building record: observed slot behaviour,” and “Candidate worker-count slot”).

For `workers.bin`, a writer/reader trace verifies a current-writer record consisting of a 0x728-byte base plus optional 9-byte and 128-byte tails gated by bytes at +0x700 and +0x70c. The bounded OpenRepublic walker frames that schema. The N22 sample’s 19,640 records reached exact EOF (OBSERVED), but no matching package/internal version was confirmed. Building-table references exist, while home, workplace, family, vehicle, and other worker-field meanings remain UNKNOWN; candidate home/work slots are INFERRED only ([REVERSE_ENGINEERING_LEDGER.md](REVERSE_ENGINEERING_LEDGER.md), “workers.bin framing investigation”).

### Economy features: construction, population, trade, scenarios, and controllers

Synthetic construction sites are now opt-in in the economy and native desktop sandbox. A site can receive material hauls, accumulate work, and complete in place under OpenRepublic-authored rules. Scenario scoring verifies one and two site completions; the native sandbox UI showed placement and inspector state, but GUI material hauling and completion have not been exercised. The site renders as the building with a progress-scaled display height. `--native-construction-sites` is used with `--native-economy`; it selects a synthetic sandbox catalog with build requirements. This does not interpret imported WRSR `COST_*` fields and does not establish WRSR construction behavior ([CONSTRUCTION_SITES.md](CONSTRUCTION_SITES.md), opening, “Desktop sandbox (opt-in),” and “In-scene presentation”).

Population/workforce and border trade remain OpenRepublic synthetic systems. Population rules and worker allocation are catalog opt-ins; trade provides catalog prices, treasury, and import/export commands. Neither feature establishes WRSR formulas or parity ([POPULATION.md](POPULATION.md), “Evidence boundary”; [TRADE.md](TRADE.md), opening and command sections).

The synthetic scenario suite now includes construction supply, trade, population, and utility cases with deterministic scoring and baseline reports. `tools/scenario_score.py` scores named fixtures. `tools/llm_republic.py --scenario <name>` and `tools/republic_tournament.py --scenario <name>` run controller/scenario workflows; tournament repeats and fixed final ticks support more comparable summaries. Fixture metrics are authored economy quantities, not WRSR metrics. Tests use a scripted backend; custom utility catalogs are not wired into the tournament path ([SCENARIOS.md](SCENARIOS.md), “Run a deterministic score,” “Metric and evidence boundary,” and “LLM controllers and tournament baseline”).

### Process and verification lessons

- Verify that a client build actually succeeded, inspect its result, and only then commit app changes. A malformed inspector string escaped one commit and was fixed immediately afterward (PROGRESS_LOG.md, true Git interval 15:03–15:05 EDT).
- Treat a worker’s “complete” report as a claim to verify. Post-merge scoring found construction supply scenarios completing zero sites; replanning fixed the measured cases to 1/1 and 2/2 (PROGRESS_LOG.md, true Git interval 14:56–15:02 EDT).
- Codex authentication/usage limits blocked bridge workers temporarily. Once login was restored, the bridge was recovered by stopping the stale bridge engine/host, backing up the bridge database, removing the unresumable thread row from that database, and restarting the bridge so the engine reported ready. These were bridge-local operational actions; they do not imply project code changes (PROGRESS_LOG.md, true Git interval 11:18–11:52 EDT).
- The original-game screenshot attempt reached the main menu but could not be controlled by the available UI routes. The game was closed without touching saves. The N22 comparison therefore still requires a manual load by the owner or a working input route (PROGRESS_LOG.md, true Git interval 10:36 EDT).
- A GUI construction-site haul session was stopped when a separate app instance with real content became foregrounded. Avoid interacting with an instance unless its identity and fixture are clear; the GUI completion path remains unverified (PROGRESS_LOG.md, true Git interval 15:09–15:11 EDT).

## Open risks

- Header option labels and most header tail semantics are unknown; no water-level or world-size decoder is justified yet.
- Road width, lane count, speed, surface, and construction cost remain unresolved despite traced constants and observed spacing.
- Building-state slot meanings and worker-to-building relationship fields remain unknown; the +0x4a0 employee-count theory is uncorroborated.
- The current worker reader is for the traced writer schema; older internal-version branches need separate support/evidence.
- Construction, population, and trade are synthetic OpenRepublic rules; imported definitions do not establish their native-game semantics.
- GUI construction hauling/completion and the resulting site visual still need a controlled session with the sandbox catalog.
- The N22 screenshot comparison is pending manual game loading. Showcase captures and frame-time measurements are scene-, build-, and hardware-specific.
- Scenario scores and controller comparisons are sensitive to fixture, final tick, and repeat count; avoid broad conclusions from one run.
- Keep proprietary game files, saves, exact fingerprints, private captures, and decompilation outputs outside Git.
