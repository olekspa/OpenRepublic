# Graphics and performance direction

## Today (VERIFIED on an RTX 5070 Ti, DirectX 12, Wicked Engine pinned revision)
`--graphics "key=value;..."` (also the type `runtime::GraphicsSettings`, intended for the agent interface) controls: `upscaler` (`none`, `fsr2_quality|balanced|performance|ultra_performance`, `dlss` reserved), `ao` (`off|ssao|hbao|msao|rtao`), `rt_reflections`, `rt_diffuse`, `ssr`, `fxaa`, `bloom`, `exposure`, `sharpen`. Unsupported features are logged, never ignored silently. Captures wait 48 frames per view when temporal features are on so FSR2/ray-tracing history matches the view (ghosting otherwise). Example: `--graphics "upscaler=fsr2_quality;ao=rtao;rt_reflections=on;rt_diffuse=on;fxaa=on"`.

## DLSS 4.x / frame generation (planned, not integrated)
Wicked Engine ships FSR2 and hardware ray tracing but no NVIDIA upscaler. DLSS super resolution, ray reconstruction and multi-frame generation require the NVIDIA Streamline SDK (DX12 proxy swap chain, motion vectors, depth, exposure and UI-excluded colour inputs). Plan: keep `runtime::Upscaler` as the neutral interface; add a Streamline-backed implementation behind it once the SDK terms are accepted and the renderer exposes motion vectors/jitter; `upscaler=dlss` already parses and reports "unavailable" until then. Neural-rendering features beyond what Streamline exposes publicly are out of scope until an SDK exists.

Integration points found in the pinned Wicked Engine (OBSERVED by reading the source, nothing built yet):
- Device/swap chain: `GraphicsDevice_DX12` loads `D3D12CreateDevice` at `wiGraphicsDevice_DX12.cpp:2278` and creates the swap chain in `CreateSwapChain` (`:3096`, `CreateSwapChainForHwnd` at `:3201`). Streamline needs its interposer loaded before device creation and a proxy swap chain, so this is a vendored-engine change (patch or fork), not an app-side one.
- Upscaler inputs already exist for FSR2 in `RenderPath3D`: camera jitter (`camera->jitter = fsr2Resources.GetJitter()`, `wiRenderPath3D.cpp:424`), `rtVelocity` motion vectors, `depthBuffer_Copy`, and the call site `wi::renderer::Postprocess_FSR2(...)` (`:2352`). A DLSS evaluation would replace that call with the same inputs plus an exposure texture.
- OBSERVED (read 2026-10-22 from the Streamline repository, not legal advice): the repository `license.txt` is an MIT-style grant, except `sl_nvperf.h`/`sl_nvperf.dll`, which fall under the separate Nsight Perf SDK licence; the DLSS-G plugin is shipped as prebuilt DLLs only and release binaries come from the repository's releases page. The programming guides cover DLSS super resolution, frame generation, Reflex and NIS; ray reconstruction and multi-frame generation were not listed on the page I read. UNKNOWN: the redistribution terms of the DLSS runtime itself (`nvngx_dlss.dll`), and whether this MIT repository may ship any Streamline binary (the plan is to download them at build time and never commit them). Frame Generation additionally needs UI-free colour and HUD-less buffers that this renderer does not separate yet.

## Performance (planned)
- Simulation: the economy production phase runs on worker threads for worlds of 1024+ buildings (`economy::SetProductionThreads`); a test checks the state hash equals the serial path. Haul movement (which couples buildings) is still serial; no speedup has been measured.
- Rendering: instancing is already used for placed buildings (one mesh per type). Next: LOD selection from the building definitions' LOD fields (loader defaults 1000/2000), frustum/occlusion handled by Wicked, texture streaming for large maps.
- Compute offload candidates: terrain tessellation/normal generation, vehicle/path queries, road graph rasterization.

## Streamline integration checklist (OBSERVED from NVIDIA's ProgrammingGuide.md, 2026-10-22; not yet implemented)
1. Load `sl.interposer.dll` by full path after verifying its signature; ship `sl.common.dll` plus the feature DLLs used (`sl.dlss.dll`, `nvngx_dlss.dll`). Unsigned/self-built DLLs only for development.
2. `slInit` before any DXGI/D3D12 call: `renderAPI = eD3D12`, `featuresToLoad`, log paths, `eUseFrameBasedResourceTagging`.
3. Create the factory/device through the interposer's exports, or create natively and call `slSetD3DDevice` immediately; check `slGetFeatureRequirements` and `slIsFeatureSupported` per adapter.
4. Swap chain/queues: Streamline hooks the first swap chain; `presentCommon()` must run exactly once per frame.
5. Per frame: `slGetNewFrameToken`, `slSetConstants` (row-major unjittered matrices, jitter offset, camera data, depth/motion flags), `slDLSSSetOptions` (render resolution from `slDLSSGetOptimalSettings`), `slSetTagForFrame` for depth, motion vectors, scaling input/output colour (frame generation also HUD-less colour), then `slEvaluateFeature` where FSR2 is evaluated now. DLSS-G uses the Present marker instead.
6. `slShutdown` at exit.
Mapping onto the engine: step 5's inputs correspond to `rtVelocity`, `depthBuffer_Copy`, the FSR2 jitter and `rt_read`/`rtFSR[0]` at the `Postprocess_FSR2` call; steps 1-4 need changes inside the vendored `GraphicsDevice_DX12`, which is why this has not been started: it needs a decision to patch or fork the pinned Wicked Engine submodule.

## Modern region view and showcase captures (2026-10-22, VERIFIED on an RTX 5070 Ti by capture and by an interactive run)
- `--modern` turns the interactive map-region view into the next-generation look; `--showcase-capture <png> --showcase-look enhanced|baseline --showcase-camera <yaw -180..180> <elevation 5..75> <distance factor> --showcase-sun <elevation 2..80> <yaw offset>` captures matched pairs from the same camera (baseline = the plain preview). Example hero: `--map-building 61 --map-region --map-radius 250 --map-lod 0 --showcase-camera -120 16 0.9 --showcase-sun 17 45`.
- What the enhanced look contains: Wicked's physically based sky with aerial perspective, volumetric clouds and valley fog; a 1435x1435 far landscape out to ~7 km sampled from the real heightmap plus a presentation-only relief boost for hills and mountains (INFERRED styling); a lake/sea where the map dips below zero (level 0 is an INFERRED choice, now supported by the shared waterriver `$HEIGHT 0` setting recorded in docs/MAP_WATER_DATA.md, though the per-map rule is still UNKNOWN); shaded terrain with a grass detail texture; roads along decoded segment polylines (curves) with an asphalt texture, edge lines and a dashed centre line; procedural trees, shrubs, vehicles, utility poles with wires, lamps, a pylon line, a railway, chimneys with smoke (src/procgeo meshes, OpenRepublic-authored); bloom, RTAO, RT reflections, FXAA, ACES tonemapping and light shafts.
- Local-only authenticity (never committed, D-005): with a WRSR install as `--content-root` the ground uses the install's `grassrock1` tile and its `grass1bump` normal map and the scatter uses the install's tree meshes with alpha-tested leaf cards. Without an install the procedural fallbacks are used.
- Known limits: the sun must not be placed low in front of the camera (the ground goes black); ocean wave amplitude above a few metres can flood the town in captures; building facades are lifted with a faint emissive stand-in for bounced light; vehicles/props/trees are not WRSR content or placements; real tree, rail and power-line placement is being decoded (workers TREES-BIN, OVERLAYS).

## Showcase performance (2026-10-23)

- The 1435x1435 far-terrain height boost, shading/vertex generation, and normal generation now use Wicked's job system across independent Z rows. Each row writes to pre-sized output arrays at its original vertex indices; the calculations and mesh topology remain unchanged. This is a source-level optimization intended to preserve the image, but image identity is **UNKNOWN** until matched captures can be compared.
- Enhanced startup now logs elapsed milliseconds for `CreateMapRegionPreview`, `PrepareShowcaseTerrain`, `BuildShowcaseWorld`, each far-terrain generation stage, `BuildShowcaseProps`, individual linear-network reads/decodes, `LoadTreePlacements`, real tree-mesh loading, and procedural texture creation. These logs have not yet been collected from a successful region-view run.
- One matched Windows Release capture run per version used building 61, 250 m, LOD 0, enhanced look, camera `-120 16 0.9`, and sun `17 45`. Process wall time from launch through capture exit was **16.19 s** on committed source and **15.14 s** with the parallel terrain loops (one sample each, a 1.05 s / 6.5% lower process wall time). This includes startup, scene construction, rendering and capture exit; it is not a repeated statistical benchmark or isolated scene-build time.
- Both PNGs were 1260x748. Their RGB mean absolute difference was **0.1373 / 255** across 2,827,440 channel values (maximum channel delta 68); side-by-side inspection showed the same scene framing and appearance. This small but nonzero image delta means exact pixel identity is not established; the scene look is visually unchanged in this pair.
- The new elapsed-millisecond stage messages are present in source, but the per-stage values were not captured to a durable log in these runs. Interactive 5-second `Modern view: N fps` samples were also not obtained, so frame-rate change is **UNKNOWN**. The historical ~100 fps note above is an uncontrolled observation and is not a benchmark for this scene.
- Repeat the paired run several times and capture the application's stage/FPS log output to establish variance and isolate scene-build versus capture time. Keep all local game data and captures outside this repository.

## Building LOD (2026-10-23)

- `--map-lod 0|1|2` retains the existing fixed selection and downward fallback. `--map-lod auto` opts into per-instance distance selection and permits LOD0, LOD1, and LOD2, subject to each type having usable, aligned assets. Default switch distances are 250 m (LOD0/1) and 700 m (LOD1/2); `--map-lod-distances near,far` changes them in metres. An 8% hysteresis band reduces repeated swaps around both boundaries. These are OpenRepublic presentation settings, not recovered WRSR thresholds; the loader-number consumer and units remain **UNKNOWN**.
- Dynamic loading compares every candidate's source-space minimum/maximum bounds and normalization scale against that type's first loaded candidate. A candidate outside the 1% footprint tolerance (with 0.05 m minimum tolerance) is rejected for swaps. Missing or failed tiers fall back to an available tier. `MIRRORZ_` is applied independently to every candidate. The region instance cap is 10,000 and the type cache cap is 160.
- Capture telemetry samples 48 application-update frame intervals after the showcase path's 12-second warmup and logs average/worst `dt` plus the derived update rate. This is not GPU-only timing and is a short sample.
- **OBSERVED, invalid performance sample:** a fixed LOD0 run on the installed DLC2 Asia terrain selected 298 placements around placement index 113, but its content root resolved 0 building instances (13 unresolved types). The empty-building scene capture completed at 1260x748 with 64.505% depth coverage; its 48-frame update sample was 4.17 ms average, 4.30 ms worst (239.9 update-dt fps). Those numbers do not measure building LOD performance. The DLC2 content root did not contain the aggregate `buildings/buildingtypes.ini` required by the current importer, and the base catalog did not resolve the DLC2-prefixed types.
- **UNKNOWN / not measured:** no valid fixed-LOD0 versus dynamic-LOD pair with rendered buildings was obtained; therefore building-LOD frame-time change, triangle reduction, and visual alignment on real LOD assets remain unmeasured. Alignment checking is implemented in the preview path, but this run exercised none of those candidates. Do not treat the empty-region timing above as a performance result. A matched run still needs a map/content root pair whose placed types resolve through the current aggregate type catalog.

App frame rates in the last sample were 101 native, 70 FSR2 Quality, 70 DLSS Quality, 75 DLSS Performance, not a controlled GPU-bound measurement. Not done: Frame Generation, Ray Reconstruction, temporal-quality proof beyond a short moving-camera screen, shipping any NVIDIA binary (never commit them), integrating the patches into the public build.
- **Not implemented:** real WRSR terrain-texture blending (shaders are compiled bytecode), authentic water rules, real pole/pylon semantics, runtime re-baking of terrain colours, a faint slope grid on steep distant terrain.
